### P0-1 多部分频道发帖绕过授权：任何 agent token 可以"用户"身份跨赛事发帖

> **状态：已修复（2026-09-09）**。multipart 分支入口处拒绝带 agent principal 的请求（400，agent 走 JSON 面）；无 token 的用户 multipart 面行为不变。回归：`test/run/channel-multipart-auth.test.ts`。

**位置**：`apps/server/src/run/routes.ts:657-676` + `apps/server/src/run/channels-post.ts:193-195`

路由的 multipart 分支**在取 principal 之前**执行，并把 `author` 硬编码为 `{ type: "user" }`：

```ts
if (contentType === "multipart/form-data") {
  const form = await c.req.formData()
  ...
  const message = await agentService.channels.postWithUpload({
    channelKey,
    author: { type: "user" },   // ← 硬编码，绕过 resolveAuthor 的全部 scope 规则
    ...
```

而 `agentAuth` 的 `verdict` 对 `POST /api/channels/:key/messages` 两种角色都放行（`infrastructure/agent-auth.ts:66-69`）。`resolveAuthor` 只在 `author.type === "agent"` 时才校验"是否属于该题目 / 该 event"（`run/channels-post.ts:196-243`）。

**实证**（用 e1 的 solver token 向 e2 的 `team:c2` 发帖）：

```
multipart POST team:c2 by solver-of-e1 -> 201
  {"channelKey":"team:c2","authorType":"user","authorName":"用户","body":"CROSS-EVENT WRITE BY SOLVER"}
JSON    POST team:c2 by solver-of-e1 -> 400 无权向该频道发帖（不属于此题目，也非本 event 调度者）
```

JSON 路径正确拒绝，multipart 路径 201 写入成功。后果：任意 solver 可冒充用户向任意赛事的任意频道写消息、向 `dm:<victim>` 投递紧急唤醒（`urgent` 默认 true），并把文件写进别人题目的 `shared/upload-*/`。

**修复方向**：multipart 分支也走 `principalOf(c)`；带 token 时要么直接拒绝（要求 agent 用 JSON），要么把 principal 传入让 `resolveAuthor` 的 scope 规则生效。顺带在 `resolveAuthor` 的 user 分支加一层"仅无 token 请求可达"的断言。

### P0-3 平台凭证在跨源重定向时泄露

> **状态：已修复（2026-09-09）**。`PlatformHttp.request` 改 `redirect: "manual"`：同源跳转最多 5 跳、逐跳重算认证头；跨源 3xx 不跟随、携状态走既有失败路径。回归：`test/platforms/redirect.test.ts`。

### P0-4 `relay.ts` 破坏所有 gzip 响应，且掐断长流

> **状态：已修复（2026-09-09）**。上游 fetch 加 `decompress: false`（字节与头一致透传），`Bun.serve` 加 `idleTimeout: 255`；gzip 完整性 / 15s 流间隔 / POST 透传三项运行时验证通过。

**位置**：`apps/server/scripts/relay.ts:34`、`:19-21`

```ts
return new Response(res.body, res)   // body 已被运行时解压，但 res 带着 content-encoding: gzip
```

**实证**：

```
upstream gz len: 66 | relay bytes: 3026
relay content-encoding: gzip | content-length: 3026
is relay body gzip? false
relay body prefix: {"hello":"world","pad":"xxxxxxxx...
```

任何解码响应的客户端都会拿到 `ZlibError`（验证时 fetch 直接抛错）。relay 是固定端点 LLM 网关的官方接入路径，这条 bug 意味着经 relay 的模型调用全部失败。

另：relay 未设 `idleTimeout`，`Bun.serve` 默认 10s 会掐断长流（实测 15s 间隔的流在 12s 处 `socket closed`）。推理模型经常 >10s 不出 chunk，**流式调用会间歇失败**。

**修复方向**：`fetch(upstream, { ..., decompress: false })` 让字节与头一致（或从响应头删除 `content-encoding`/`content-length`）；`Bun.serve({ port, idleTimeout: 255, fetch })`。

### P0-5 `channels.read()` 超出 limit 的积压消息永久丢失

> **状态：已修复（2026-09-09）**。agent 拉取路径改为前向分页（游标上方最旧窗口），游标只越过实际交付的前缀；SDK `read` 返回 `MessageList`（messages/has_more/next_after），GUIDE、prompt 签名与契约探针同步更新。回归：`channels.test.ts` 前向分页组 + `contract.py` 分页探针。

**位置**：`apps/sdk/python/aegisx/channels.py:68-91` + `apps/server/src/run/channels-reads.ts:32-63,104-127`

`listMessages` 返回 `(after, …)` 区间内**最新**的 limit 条（`desc().limit(limit+1).toReversed()`），而 `readForAgent` 把读游标推进到窗口里**最后一条**（=最新一条）：

```ts
if (opts.markRead !== false && result.items.length > 0) {
  ctx.markRead(key, readerKey, result.items[result.items.length - 1].id)
}
```

该游标与**投递引擎共用**（`run/channels-delivery.ts:69` 的 `readCursor`）。积压 > 50（默认 `DEFAULT_PAGE = 50`，`channels-reads.ts:24`）时，`(cursor, 窗口起点)` 之间的消息既不被返回、也永远不会被投递。SDK 还丢掉了服务端的 `hasMore`（`channels.py:83-91`），调用方连"被截断"都感知不到。

**实证**（代码路径确认）：120 条未读 + `limit=50` → 只返回 id 71–120，游标跳到 120，id 1–70 永久丢失。

**修复方向**：agent 读路径改为**从游标向前分页**（`asc` 取最旧窗口），或仅在 `!hasMore` 时推进游标，并把 `hasMore` 透传给 SDK。

### P0-6 前端在首个 snapshot 之前的 `message.committed` 被丢弃

> **状态：已修复（2026-09-09）**。丢弃条件改为「已应用过更旧 epoch 的 snapshot」才丢弃：首个 snapshot 之前的提交保留，reset 窗口的幽灵提交仍被丢弃。回归：`apps/web/tests/conversation-store.test.ts` 两个用例。

**位置**：`apps/web/src/stream/conversation-store.ts:315-324`

```ts
if (this.snapshotEpochs.get(event.agentId) !== this.epochOf(event.agentId)) return
```

`snapshotEpochs` 只由 `applySnapshot` 写入（`:303`）。首个 snapshot 之前它是 `undefined`，而 `epochOf` 返回 `0`，`undefined !== 0` 恒真 → **所有早到的 committed 行被静默丢弃**。`connect()`（`:442-481`）只 seed `ready`/`agent.updated`/context/queue/activity/in-flight tools，不 seed committed 行，也没有周期性消息轮询，所以这一行永久消失。


**修复方向**：只在"确实应用过更旧 epoch 的 snapshot"时才拒绝：

```ts

if (applied !== undefined && applied !== this.epochOf(event.agentId)) return
```

### P1-2 `DbSessionManager` 无关闭守卫，dispose 后仍可写

**位置**：`apps/server/src/agents/db-session-manager.ts:174-188`、`apps/server/src/agents/host-session.ts:245-248`

manager 没有 `closed`/`dispose` 概念，`nextSeq` 是每实例内存值。`HostAgentSession.dispose()` 只 `unsubscribe + session.dispose()`，而 pi 的 abort **不中断进行中的工具调用**（`run/service.ts:317-325` 自己注释了这点）。于是 `forceAbortAgent` 之后仍在跑的 bash 可能继续触发 `message_end → appendMessage`；若此时 agent 被重开，`run/agent-factory.ts:816-822` 会为同一 sessionId 建**第二个 manager**，两者写入的 `seq` 可能重叠 → `UNIQUE(sessionId, seq)` 抛错，且新旧 turn 交错进同一会话。

机制成立（已核对 pi 的 `abortController` 与 dispose 路径），未构造出活复现——触发需要"超时强杀后又被重开"的窄时序。

另：`DbSessionManager.open`（`:118-139`）只读 `cwd`/`createdAt`，不校验 session 行归属；`session_entries.agentId` 与 `sessions.agentId` 是两个独立 FK，无 DB 约束（`db/schema.ts:239-244`）。

**修复方向**：manager 加 `closed` 标志，`commit()`/`load()` 在 closed 时抛/忽略；`open()` 校验归属。

## 测试缺口（按风险排序）

`bun test --max-concurrency 1` 15.4s / 389 pass，速度很好，但覆盖面有明确空洞：
