# 交互层走查：用起来难受的点（2026-08-18）

> 范围：`apps/web` 交互形态与数据刷新方式（不含服务端正确性，见 `code-review-2025-08-16.md`；前端工程质量见 `frontend-review-2026-08-17.md`）。
> 方法：核心链路（事件 → 题目 → run → 对话）逐文件走查 + 轮询/请求模式核对。
> 结论：核心链路代码质量不差，难受的不是功能缺失，是**交互形态和数据刷新方式**。按对日常使用的影响排序。

---

## 主要痛点

### 1. 监控/干预的主战场是一个 Modal，不是页面

- run 的全部体验（对话/频道/文件/概览）塞在 `AgentDialog`（`agent-dialog.tsx`）——一个 `h-[min(85svh,52rem)]` 的弹窗，从 graph 节点点出来，**没有 URL、刷新即丢、一次只能看一个**
- 层级是：赛事页左侧 tab（4 个）→ Agents tab 内部又一层 tab（计划/时间线/题目/Agents，`event-page.tsx:413`）→ 点节点开 modal → modal 里再一层 tab（6 个）→ composer 里还藏个命令菜单。**三层 tab 套 modal**
- 比赛中最高频的姿态是"左边盯 solver A 出力，右边看 solver B 是否卡死"——modal 形态下做不到；100+ run 的赛事想快速扫一遍状态，得在 ReactFlow graph（`agents-graph.tsx`）上逐个点节点开弹窗
- **改法**：run 提升为一级路由 `/events/:id/runs/:runId`（可开多个浏览器 tab、可深链、可收藏），graph 退化为总览关系图而非操作入口

### 2. 轮询密度与 SSE 割裂，"感觉不跟手"

- 对话流有 SSE，但 fleet/queue/usage/scheduler 全是 5s 轮询，channels 是 3s 双轮询（`channels-view.tsx:389,639`）。状态变化最多滞后 5 秒，操作后（暂停调度、入队）也是等轮询才回显
- **实锤一个 bug 级问题**：概览 tab 的 fleet 查询（`event-summary.tsx:74-81`）还是旧的 N+1 写法——`listEventRuns` + `Promise.all(getRun×N)`，每 5 秒对服务器发 N+1 个请求（50 个 run = 每 5s 51 个请求）；而 Agents tab 已换成单一 `/fleet` 聚合端点。**两者共用同一个 queryKey 却是两个不同的 queryFn 和返回形状**——切 tab 就互相踩缓存、闪 spinner、重新拉全量
- **改法**：概览改用 `getFleet`；中期把 run/agent 状态变化也走 SSE（服务端已有 LiveBus 推送管道，只是 web 没订阅状态类事件）

### 3. 启动任务表单太重，高频操作没有快路径

- `create-run-dialog.tsx`：启动方式 radio + 题目选择 + solver 数 + 模型 + 超时 + strategy + 逐 solver 高级 + 一大块"容器工具箱"说明 Alert。比赛中可能要启动几十次，**每次都过一遍全量表单**
- 没有"记住上次配置"、没有失败后"原配置重跑"一键入口（只能重新走表单）
- 说明性文案（容器工具箱 Alert）在 `run-overview.tsx` 里也永久占一块——第一次有用，第十次是噪音
- **改法**：默认折叠成"题名 + 模型 + 启动"三件事，其余进"高级"；记住上次的 solver 数/超时/模型；run 失败/超时处加"重跑"按钮直接复用原参数

### 4. 主 composer 能力弱，且和频道 composer 不一致

- 主对话输入是**单行 `<Input>`**（`message-input.tsx:107`）——无换行、无 Shift+Enter；而频道输入反而是 Textarea + Enter/Shift-Enter（`channels-view.tsx:298`）。主次颠倒，CTF 指令常带多行 payload/代码块
- slash 命令（/compact /new /close）藏在"+"菜单里，输入 `/` 没有任何提示或补全
- 发送无乐观回显（`conversation-store.ts` 的 `pending` 字段是死标志，前端审查 #11 已记录）——点了发送要等 SSE 回显才知道成功
- steer/引导 vs followUp/追问 的切换是个运行中才出现的小箭头菜单，可发现性差

### 5. Provider/模型配置摩擦集中在"第一次跑通"

- 不服务 `GET /models` 的 LLM 网关（DASCTF 这类）要**手动逐个加模型**；relay 还得另开终端 `bun run relay` 手动起、一个 upstream 一个进程（README 自己也承认）
- 没有"发一条测试消息验证整条链路"的入口——配置对不对，要起一个真 run 才知道，错了就烧一次启动+等待
- **改法**：provider 详情页加"测试对话"（一次 1-token 请求）；relay 能力收进服务端进程内（已有 strip-path 实现，改成管理界面可配置的内置代理）

## 建议整改批次

1. **第一刀（半天，纯赚）**：概览 fleet 改聚合端点（修缓存踩踏）＋主 composer 换 Textarea＋发送乐观回显＋AgentDialog not-found 分支
2. **第二刀（1–2 天，形态级改善）**：run 工作区提升为独立路由页，AgentDialog 变薄入口；创建任务对话框默认收起高级项＋记住上次配置＋失败重跑
3. **第三刀（可选）**：状态类事件走 SSE 替代轮询；provider 测试对话；relay 内置

判断：1+2 能消掉"难受"的大头。
